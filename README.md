# zhen-app — the app

An Xcode project. No Swift package of its own: the sources here are app-target sources,
so a view is edited with a live canvas instead of through a package boundary.

```
Zhen.xcodeproj     generated by ../Scripts/generate-xcodeproj.py — that script owns it
Zhen/              views and view models
  Design/          the design system: tokens, components, patterns, fixtures
ZhenTests/         layout, contrast, keyboard, symbols, snapshots
Resources/         Info.plist and the asset catalogue
```

## Two things worth knowing before editing

**The project is generated, and adding a file does not regenerate it.** `Zhen/` and
`ZhenTests/` are synchronized root groups, so a new Swift file is in the target the
moment it is on disk. The generator owns structure — targets, settings, schemes — and
the folder owns files. CI checks that regenerating is byte-identical, which stays
meaningful precisely because ordinary work does not change it.

**The app target is `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`.** Everything here is a
view, a view model or a value one of them reads, so that is right. The scanning half
lives in the `zhen` package as `ZhenScan`, non-isolated, and it stays there: if
something in this project ever seems to need to move a socket in here, that is UI
leaking into the scanner rather than a reason to relax the setting.

## Build

```sh
open Zhen.xcodeproj                   # previews, canvas, the usual
../Scripts/build-app.sh release       # the signed, helper-embedding bundle
```

`build-app.sh` takes the executable out of Xcode's build and assembles the bundle by
hand, because three things in that layout are not Xcode's to decide: the `Info.plist` is
generated from the scanner's own Bonjour vocabulary, the daemon plist has to sit exactly
where `SMAppService` looks, and the signing is inside-out with a team check that fails at
build time rather than at a user's first launch.

Design system and rationale: `../Docs/A1-design-system-foundations.md` onward.
